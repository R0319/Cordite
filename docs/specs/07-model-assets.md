# 07. モデル / テクスチャ仕様（作者用）🟡 仮

> **範囲**: 3Dモデルとテクスチャの制作基準。作者（あなた）が手作業で制作するときのリファレンス。
> **🔵 検討中**: Claude（または他のAI）にモデル・テクスチャを生成させる方式を試行中 → [生成方式の試作比較](#モデル生成方式の試作比較-検討中)。採用するかは作者が試作を見て決める。
> ここに書くのは「どういう形式・命名・解像度で作ればコードとgunpackに噛み合うか」の取り決め。
> 用語・凡例は [README.md](README.md) を参照。数値はすべて仮確定（後で調整）。

## 制作ツール / 出力形式（仮）

- 推奨エディタ: Blockbench（標準機能のみで制作可能。GeckoLib等の専用プラグインは不要）
- モデル形式: Blockbench標準の「Bedrock Edition」形式（`geometry.json` + `animation.json`）。ボーン付きモデル・キーフレームアニメーション前提 → [06-animations.md](06-animations.md#アニメーション作成方式-仮)
- 1銃 = **viewmodel（一人称用）** + **worldmodel（三人称用）** の2モデルファイル + 1テクスチャ（テクスチャは共用、gunpack内に同梱）
  - 理由: 一人称は手元の誇張したパースや壁めり込み防止のため専用モデルが必要 → [06-animations.md](06-animations.md#モデル構成一人称三人称分離) と連動
  - ボーン命名規約は両モデルで共通（下記）にし、コード側のアニメーション再生ロジックを共有できるようにする
- 座標系・スケール: Minecraft標準（16px = 1ブロック）。銃の全長はモデル上で実寸に近い比率で作成 → 目安と手順は [新しい銃を作るときの手順](#新しい銃を作るときの手順おすすめ-仮)

## 制作上の制約（重要）🟡 仮

自前パーサ（[06-animations.md](06-animations.md#アニメーション作成方式-仮)）が読める範囲でモデルを作るための制約。

- **キューブのみで作る（メッシュ不可）**: Bedrock Edition形式はキューブ＋ボーン構成のみで、Blockbenchのメッシュ要素（Generic Model形式専用）はBE形式にエクスポートできない。**Meshy等のAI生成・メッシュインポート系プラグインの出力はそのままパイプラインに載らない**（形状の参考資料＝リモデリングの下絵として使うのは可）。
  - 🔵 **メッシュ対応（作者のローカルで実装済み・未プッシュ）**: Blockbench プラグイン **Meshy**（作者 Shadowkitten47。AI 生成サービスの Meshy とは別物）を使うと、メッシュを Bedrock 形式のボーンの `poly_mesh` として書き出せる。Blockbench 本体の Bedrock 形式はメッシュを保存できない（本体ソース `js/formats/bedrock/bedrock.js` で確認）ので、メッシュを使うにはこのプラグインが必須。
    - `poly_mesh` の形（プラグインのソースで確認）: `positions`（キューブの `origin` と同じ座標系の絶対座標）／`normals`／`uvs`（`normalized_uvs: true` なら 0〜1、**V は下端基準**）／`polys`（`[位置, 法線, UV]` の4頂点。三角形は先頭頂点を4つ目に重ねる）
    - ボーン単位で持つので、アニメーション（ボーン名で動かす）はキューブと同じく効く。1ボーンにキューブとメッシュを混在できる
    - 描画は `entityCutoutNoCull`（裏面も描く）なので、ポリゴンの頂点の並び順（表裏）は問題にならない
- **キーフレームは数値のみ（Molang式禁止）**: アニメーション値に式・変数を入れない → [06-animations.md](06-animations.md#アニメーション作成方式-仮)
- **`format_version`**: geometryは `1.21.0`、animationは `1.8.0`（Blockbenchの既定エクスポート）。animation側は`1.8.0`以外だとローダーが警告を出す。
- **UV方式は Per-face UV** ✅（Box UVは 🔵検討中 から確定）。
  - **Box UV のキューブは描画されない**。ローダーが読み飛ばし、`latest.log` に「Box UV形式のキューブをスキップしました」と出す。描きたいパーツを誤ってBox UVにすると<b>無言で消える</b>ので注意。
  - これは逆に**位置合わせ専用の箱を隠す手段としても使っている**: `right_hand`/`left_hand` の腕プレースホルダはBox UVにしてあるため、寸法だけがコードに使われ、描画はされない。
- **`description.identifier`**: 現状 `geometry.unknown` のまま。ローダーはファイル内の**最初のジオメトリ**を無条件で使うので動作に影響はないが、1ファイルに複数モデルを入れる運用になる前に `geometry.<gunId>` へ直しておくこと。
- **`texture_width`/`texture_height` と実テクスチャの解像度は一致しなくてよい**。UVは宣言サイズで正規化されるので、glockのように「宣言128・実テクスチャ256」なら2倍解像度として正しく貼られる。

## ボーン命名規約（重要・アニメーションと連動）

アニメーションとアタッチメント装着位置をコード側から参照するため、ボーン名は固定する。

下表は **glock（プロトタイプ実装）の実際の構成**に合わせてある。名前をコード側が直接参照するものには「コード参照」を付けた——**これらの名前を変えるとその機能が黙って止まる**。

| ボーン名 | 親 | 部位 | コード参照 |
|---------|----|------|-----------|
| `root` | — | モデル全体の基準。アニメーションの反動・リロードはここを動かす | — |
| `receiver` | `root` | レシーバー（機関部） | — |
| `barrel` | `root` | バレル | — |
| `chamber` | `barrel` | 薬室 | — |
| `bolt` | `root` | ボルト/スライド（射撃・ボルト操作で可動） | — |
| `trigger` | `root` | トリガー | — |
| `magazin` | `root` | マガジン（リロードで着脱）。⚠️綴りに注意（`magazine`ではない） | — |
| `mag_ammo` | `magazin` | マガジン内の弾。リロード中に`scale`0で消す | — |
| `ammo` | `root` | 薬莢。**排莢クリップで多重描画される** → [animation-system.md](../design/animation-system.md#排莢薬莢は独立クリップの多重再生-アセット規約) | ✅ `"ammo"` |
| `muzzle_flash` | `root` | マズルフラッシュの位置（**cubeを持たないロケーター**） | ✅ `"muzzle_flash"` |
| `right_hand` / `left_hand` | — | 一人称の腕の基準（ハンドアンカー方式 → [06-animations.md](06-animations.md#一人称の手腕表示ハンドアンカー方式-仮)） | ✅ |
| `handguard` / `stock` / `charging_handle` / `muzzle` / `rail_top` / `rail_bottom` / `rail_side` | `root` | ⬜**未配置**（Blockbench既定位置のまま。中身が無い枠だけ存在する） | — |

- レール上のアタッチメント描画位置は gunpack JSON の座標で微調整する → [01-gunpack.md](01-gunpack.md#アタッチメント描画位置)
- ⚠️ **`muzzle` は発射エフェクトの基準に使っていない**。マズルフラッシュは専用の `muzzle_flash` ロケーターを使う（`muzzle` は未配置のまま原点近くにあるため）。`muzzle` をマズルデバイスの装着位置として使うときは、まず正しい銃口位置へ動かすこと → [02-guns.md](02-guns.md#マズルデバイス仕様)
- **モデル側にはこの表に無いボーンがあってもよい**（Blockbenchの作業上生まれる中間ボーン等）。コードは上表の「コード参照」以外の名前を見ていないので、階層を増やしても壊れない。実例: glockには `bolt` の子として `Slide`／`bone`、`right_hand`/`left_hand` の子として `rightItem`/`leftItem` がある。
- **アニメーションのクリップ名もコードが参照する**（`idle` / `take_out` / `fire` / `fire_empty` / `reload` / `reload_empty` / `inspect` / `inspect_empty` / `eject`）→ [animation-system.md](../design/animation-system.md#銃アニメーションの自動検出登録作業は不要)
- `right_hand` / `left_hand` は worldmodel には不要（三人称の腕は別方式で制御 → [06-animations.md](06-animations.md#プレイヤー本体腕体のポーズ-検討中)）
- **腕モデルの寸法（バニラ準拠・参照用）**: 通常腕（Steve型）4×12×4px、スリム腕（Alex型）3×12×4px。`right_hand`/`left_hand` 周辺の腕モデルを作る際はこの寸法を基準にする（勘で作らない）。

## 位置決め用ロケーター（表示・カメラ基準点）🟡 仮

上記のボーンとは別に、**実体を持たない位置決め専用ボーン（Bedrock形式のlocator）**を配置する。バニラMinecraftのアイテム `display`（`thirdperson_righthand`/`ground`/`fixed`等）に相当するものを、Corditeの自前レンダリング用に置き換える位置づけ。TACZ等の既存ガンMODで実績のある構成を踏襲する。

| ロケーター名 | 親 | 用途 | 状態 |
|------------|----|------|------|
| `idle_view` | **なし（ルート直下）** | 非ADS時の一人称カメラ基準位置 | ✅ 実装・配置済み |
| `iron_view` | `root` | ADS時の一人称カメラ基準位置（サイトのレティクルと連動）→ [02-guns.md](02-guns.md#サイト照準仕様) | ✅ 実装・配置済み |
| `muzzle_flash` | `root` | マズルフラッシュの発生位置 | ✅ 実装・配置済み |
| `ground` | なし | 地面ドロップ表示時の基準位置 | ✅ 実装済み・⬜未配置（原点のまま） |
| `thirdperson_hand` | — | 三人称での手持ち基準位置（**モデルの「手で握る位置」に置く**） | ✅ コード対応済み・⬜モデル未作成 → 三人称表示が崩れる原因 |
| `fixed` | — | アイテムフレーム等、固定表示の基準位置 | ✅ コード対応済み・⬜モデル未作成 |

- ⚠️ **`idle_view` と `iron_view` の親が食い違っている**（`idle_view`はルート直下、`iron_view`は`root`の子）。コードはどちらも**アニメーション適用後の位置**で読むため、`root`を動かすアニメーション中は `iron_view` だけが追従し、腰だめ⇄ADSの補間が非対称になる。どちらかに揃えること（`root`の子に統一するのが素直）。
- これらは非表示（レンダリングされない）。コード側はロケーターの**座標のみ**を読み取り、カメラや表示位置の計算に使う（回転は未使用）。
- ⚠️ **`right_hand` / `left_hand` はロケーターではなく「箱を持つボーン」**。バニラの腕モデルを重ねる位置合わせに箱の寸法を使うため、実体が要る。ただし**Box UVにしてある**ので描画はされない（下記「UV方式」）。
- Blockbench上での配置には `Cameras` プラグインを使う（プレビュー専用の補助ツールであり、ゲーム側が実際に読むのはロケーター自体の座標）。配置作業前にBlockbenchのプレビューFOVを **70**（Minecraft標準の一人称視野角）に合わせること。
- `iron_view` はサイト（アイアンサイト/光学サイト）のアタッチメント位置によって動的にズレるため、gunpack側のアタッチメント座標との連動方法は実装直前に `docs/design/animation-system.md` で詰める。
- ロケーターが回転情報を持てるかは `format_version` に依存する（古いバージョンは座標のみ）。カメラ基準に回転が必要になる場合は、対応バージョンの確認 or 通常ボーンで代用する方式を `docs/design/animation-system.md` で決める。🟡

## 新しい銃を作るときの手順（おすすめ）🟡 仮

2丁目以降を作るときに、大きさ・向き・ボーン構成がバラつかないようにするための作業手順。**厳格な規格ではなく出発点**（下記「リアル準拠にこだわらない」）。

1. **`glock.geo.json` を複製してベースにする**
   ボーン構成・ロケーター（`idle_view` / `iron_view` / `ground` / `muzzle_flash`）・腕プレースホルダ・Box UV設定が丸ごと引き継がれるので、規約から外れにくい。ゼロから作るとロケーターの置き忘れで一人称配置が既定フォールバックに落ちる。
2. **最初に「全長ぶんの箱」を1つ置き、その中に収める形でモデリングする**
   後から全体を拡縮すると子ボーンのpivotがズレて手戻りが大きい。全長の目安は下記の換算で決める。
3. **glockを同じBlockbenchシーンに並べて見比べる**
   グリップの太さ／腕プレースホルダの箱との関係が、glockと同じ感覚になっているかを目視で確認する。数値より「手に対して握れる太さに見えるか」が実質的な基準。

### 大きさの目安（出発点）

glockは実銃比で **おおむね 1px ≒ 24mm**（＝1ブロック16pxが約38cm）で作られている。全長8.18px・全高5.61px・全幅1.29pxで、実銃（186×138×32.5mm）と3軸とも23〜25mm/pxで一致する。

- 新しい銃の全長は **実銃の全長[mm] ÷ 24 ≒ px** から始めるとglockと並べて違和感が出にくい。
  - 例: AK-47（880mm）→ 約36.5px（≒2.3ブロック）／ M4A1（838mm）→ 約35px ／ M1911（216mm）→ 約9px
- ⚠️ **バニラの腕の「長さ」を定規に使わない**。腕の箱は4×12×4pxで、この換算だと幅96mm（実際の手幅とほぼ一致）に対し長さ288mm（前腕ぶんしかない）。バニラの腕がずんぐりしているだけなので、腕の長さに銃を合わせると手に対して銃が小さくなる。**合わせるのは幅（握れる太さに見えるか）**。

### リアル準拠にこだわらない（重要）

上の換算は**あくまで出発点で、実寸に忠実であることが目的ではない**。所詮アニメーションなので、表現の幅を優先して崩してよい。

- 一人称で映えるよう、可動部やサイトを実寸より大きめに作る／全長を詰めるといった誇張は歓迎（viewmodelは元々そのための分離 → [06-animations.md](06-animations.md#モデル構成一人称三人称分離)）。
- 数値が数割ずれていても問題は起きない。**銃どうしを並べたときの相対的な大きさが破綻していなければよい**。
- ただし**極端に外れると実害が出る**箇所があるので、そこだけは意識しておく:
  - **アタッチメントは銃間で使い回す**（[01-gunpack.md](01-gunpack.md)）。スケールが銃ごとにバラつくと、同じドットサイトが片方で適正・片方で巨大／極小になり、後から直す手段が無い。
  - 三人称・地面ドロップ・額縁の拡大率（`GunItemRenderer` の `THIRD_PERSON_SCALE` / `OTHER_CONTEXT_SCALE`）は**全銃共有**。片方に合わせるともう片方が崩れる。
  - マズルフラッシュの板の大きさ（`MUZZLE_FLASH_HALF_SIZE`）も現状は全銃共有。口径ごとに変えたくなった時点で、コード側をgunpackの銃別値へ出す（→ 作者から依頼する）。

### 向き・原点は揃える（見た目と違い、ここは機械的な約束）

大きさと違い、こちらは崩すと**コードのロケーター解決やアニメーション流用が壊れる**ので、glockと同じにしておく。

| 項目 | 規約（＝glockの現状） |
|-----|--------------------|
| 銃口方向 | **−Z**（`muzzle_flash` が Z=−4.07 にある） |
| 上 | **+Y** |
| 左右対称面 | **X = 0** |
| Y = 0 | グリップ底面の高さ（マガジンのフロアプレートはマイナス側へはみ出す） |
| Z = 0 | トリガー付近（glockはトリガー中心 Z≒−0.3） |

- **原点をトリガー／グリップ位置に置く**と、`right_hand` / `left_hand` プレースホルダの位置と `idle` の腕キーフレームをglockからほぼ流用できる（実銃でも構えの基準は撃つ手の位置）。
- ボア軸（銃身中心線）の高さは銃ごとに違ってよい（glockはY≒4.3）。`iron_view` は銃ごとに置き直す前提なので揃える必要はない。

## レールとアタッチメントの寸法規約 🟡 仮

上の「大きさの目安」は多少ずれても見た目の問題で済むが、**レールは銃とアタッチメントの接合面**なので、ここだけは銃をまたいで一致させる。ばらつくと「サイトが浮く／めり込む」という機能的な破綻になり、直すには全銃または全アタッチメントの作り直しが必要になる。

### 1スロットの物理長さ

gunpackはレール長を**スロット数**（`rails.length`）、アタッチメントの占有も**スロット数**（`sight.size`）で持つ（[01-gunpack.md](01-gunpack.md#レール定義銃側)）。**スロット→pxの換算係数はプロジェクトで1個**でないと、`size: 2` の意味が銃ごとに変わってしまう。

| 項目 | 実物（MIL-STD-1913） | 1px≒24mm換算 | **採用値** |
|-----|-------------------|-------------|----------|
| スロット間隔 | 10.0mm | 0.42px | **0.5px / スロット** |
| レール幅 | 21.2mm | 0.88px | **1.0px** |

- 実物換算だとサブピクセルでBlockbench上で扱いづらいため、実物比1.2倍に丸めてある。10スロットのレール＝5px。
- **レールの刻み（ノッチ）はモデルで作らない**。この寸法では1スロット0.5pxで形状として見えないので、質感はテクスチャで表現する。スロットはあくまで論理的な単位。
- レール天面の高さ（ボア軸からの距離）は**銃ごとに違ってよい**。その差は gunpack の描画位置指定が吸収する（[01-gunpack.md](01-gunpack.md#アタッチメント描画位置)）。

### アタッチメントモデルの原点

銃本体と同じく向きは **銃口方向 −Z / 上 +Y**。原点は下記に統一する。これが揃っていれば、gunpack側はレール上の1点を指定するだけで済む。

| 軸 | 位置 |
|---|---|
| X = 0 | 左右中心 |
| Y = 0 | **レール天面**（足の接地面。モデルはここから上に作る） |
| Z = 0 | そのアタッチメントが占有する**最後端スロットの中心** |

- `Z = 0` を最後端スロットに置くことで、`size` ぶんだけ前方（−Z方向）へ 0.5px 刻みで並ぶ形になり、`movable: true` のレール上でのスライドが「0.5px×スロット数」の平行移動だけで表現できる。
- `Y = 0` をレール天面にしてあるので、**足の裏が必ず Y=0 に接する**ように作ること。ここが浮いていると全銃で同じだけ浮く。

## 必要なモデルパーツ

### 銃本体
- 上記ボーンを持つ完成モデル1式
- 可動部（`bolt` / `charging_handle` / `magazin` / `trigger`）は独立ボーンで分離しておく

> **現状（glock）**: viewmodel と worldmodel は**まだ分離しておらず1モデルを全コンテキストで使い回している**。三人称・アイテムフレームの見た目が崩れるのはこのため（`thirdperson_hand`/`fixed` ロケーターも未作成）。分離方針そのものは [06-animations.md](06-animations.md) のとおり維持する。

### アタッチメント（別モデル）
アタッチメント種別ごとに独立モデル。装着はレール座標に合わせる。

- サイト（レティクルは別画像。モデルはガワのみ）→ レティクル仕様は [01-gunpack.md](01-gunpack.md#アタッチメント定義アタッチメント側)
- マズルデバイス（サプレッサー / フラッシュハイダー / マズルブレーキ / 銃剣）
- マガジン（拡張マガジンは別モデル）
- ストック（フォールディング等の可動式ストックを含む）
- ウェポンライト

## モデル生成方式の試作比較 🔵 検討中

「作者が手で作る」以外に、**モデルを生成させて作者は確認・修正に回る**方式を試す。2方式を同じ銃（M4A1）で作り、
制作コストに大差が無ければ作者の好みで採用を決める。

| | A: パーツ組立（実寸寄り） | B: ピクセル（抽象化） |
|---|---|---|
| 作り方 | 実寸（mm）で部品（バレル・ガスブロック・フロントサイト・リアサイト・レール・弾倉…）を個別に作り、ボーンへ割り当てて組み立てる。部品は単体の `.geo.json` としても出力し、同系統の別銃へ流用する | 0.5px 刻みで直接記述。回転を使わず、傾きは階段状（ドット絵の斜め線） |
| テクスチャ | 8テクセル/px（512×512）。下塗り＋縁の陰影、レールの刻み・放熱孔はテクスチャで表現 | 2テクセル/px（64×64）。平塗り＋縁取り |
| 規約との関係 | 全体寸法・ボア軸・レール（0.5px/スロット・幅1.0px）・ロケーターは**両方式で共通**（アタッチメントを使い回すため） ||

- **C の簡略版（`m4a1_mesh_lite`）**: 敵 NPC が持つ銃など、近くで見ない用途向けに面を減らした差分（C の約 4 割の面数、テクスチャ 256px）。
  丸い部品の分割数・グリップの丸めの段数・弾倉の湾曲の分割を減らし、RAS の丸穴は開けない。生成ツールの `set_detail("lite")` で切り替える。
  ⬜ ゲーム側で敵 NPC にこの簡略版を使わせる仕組み（銃 ID とは別のモデル指定）は未実装。
- **C: パーツ組立＋メッシュ**（A の派生）: 丸・斜面・曲線の部品（銃身・ハンドガード・バッファチューブ・弾倉の湾曲・グリップ・ストック・フロントサイトの塔・弾薬）を `poly_mesh` に置き換え、角張った部品はキューブのまま。組み立て（ボーン割り当て）は A と共通。メッシュ対応のローダーが前提（上記・未プッシュ）。

- **生成ツール**: `tools/modelgen/`（Python。`python3 build.py` で `generated/<方式>/` に `m4a1.geo.json`・`m4a1.png`・`m4a1_modelshot.png`・プレビュー画像を出す）。ローダーと同じ回転規則で描くプレビューを持ち、生成側が形を目視確認できる。
- **生成AIの選定**: Claude を採用。GPT-6 Astra（OpenAI）は Blender を操作してメッシュを作るのが強みだが、Blender の出力は「OBJ 書き出し → Blockbench で読み込み → ボーンへ振り分け → Meshy プラグインで `poly_mesh` 書き出し」と変換の手間がかかる。Claude はプロジェクトの規約（ボーン名・ロケーター・レール寸法）を参照しながら `.geo.json`（`poly_mesh` 含む）を直接書けるので手戻りが少ないと判断した。有機的な曲面（人型の敵など）が必要になったら再評価する。
- **見た目の値は仮置き**: `idle_view`・腕プレースホルダは glock の値を流用。`iron_view` は照準線上・`muzzle_flash` は銃口・`thirdperson_hand` はグリップ中心に計算で置いた（構造的な位置のみ）。最終位置は作者が実機で調整する。
- **写真からの輪郭抽出**: 下回り（レシーバー後部の下面・マグウェル・トリガーガード・トリガー・グリップ）と上部レシーバーの前後端は、作者提供の真横写真から輪郭を抽出して使っている。縮尺は写真のレールの刻み（MIL-STD-1913 の 10mm 間隔）から求め、生成したモデルを写真に重ねて一致を確認した。写真のグリップは Engage 系で M4A1 標準の A2 とは形が違うため、グリップ本体は A2 の特徴（軸 25°、小さな張り出し、前面中ほどの指掛け1つ、断面は前が細い卵形で前後のストラップは丸く、底は平らで角だけ丸める）で描き、取付面（上面・前面上端・張り出しの上縁）だけ写真のレシーバー形状に合わせた。A2 の真横写真での検証はまだ。写真の Engage 系の輪郭も `grip_outline_engage` として残してある。別の銃でも、真横写真＋寸法の分かる部品が1つ写っていれば同じ方法で形を取れる。
- **実寸の限界（試作で判明）**: 1px≒24mm では、フロントサイトのポスト（幅約3mm＝0.13px）やリアサイトの穴（4mm）はほぼ見えない。実寸で作る意味が出るのは輪郭・部品の比率までで、細部はテクスチャか誇張が必要。
- **未検証の点（C）**: `poly_mesh` はプラグインの書き出しと同じ形にしたが、作者ローカルのローダーが未プッシュのため、実際に読めるかは未確認。法線の X の符号はプラグイン側（Blockbench 内部座標のまま）と生成側（ファイル座標）で逆になっている可能性があり、ずれていれば陰影だけが左右反転する。
### 形の作り分け（メリハリ）🟡 仮

**全部を丸くすればよいわけではない。** 部品の素材と作り方に合わせて「丸いもの」と「角張ったもの」を描き分け、
その対比で実物らしさを出す。丸くしすぎると全体がのっぺりし、角張らせすぎると箱の寄せ集めに見える。

| 区分 | 部品の例 | 形の作り方（`tools/modelgen`） |
|-----|---------|-----------------------------|
| 握る・触れる樹脂部品 | ピストルグリップ | 断面を丸くする（`inflate_x`）。手が触れる面は全周を丸め、底など平らな面は角だけ小さく丸める |
| 樹脂の外装 | ストック、ハンドガード | 面は平ら／筒のまま、角だけ丸める（`extrude_x_beveled`・`lathe`） |
| 回転体の金属部品 | 銃身、バッファチューブ、フラッシュハイダー | 円筒（`lathe`）。段差・溝ははっきり残す |
| 削り出し・板金の金属部品 | レシーバー、弾倉、レール、サイト、トリガーガード | **角張ったまま**。丸めるとしてもごく小さな面取りまで。弾倉は箱形で稜線を立てる |

- 迷ったら実物写真で「角に光が細く入っているか（＝小さな面取り）」「面全体がなだらかに陰っているか（＝丸い）」を見て決める。
- 同じ部品の中でも面ごとに変える（グリップの前後は丸く、底は平ら）。
- 経緯: グリップを丸くして好評だった後、弾倉も丸めようとして「弾倉は基本角張っている」と指摘を受けた。

### 形の読み違いの記録と対策 🟡 仮

数値は合っていても**形の成り立ち（穴・分かれ目・向き）**を読み違えると、別物に見える。読み違えたものは原因と対策をここに残す。

| 部品 | 読み違い | 原因 | 対策（以後の手順） |
|-----|---------|-----|------------------|
| フロントサイトベース（A2） | 中身の詰まった台形のひれとして作った。実物は「A」の字の枠で、横棒の上（三角の窓）も下（前後の輪の間）も抜けている。さらに**前後が逆**（垂直の辺を後ろ、斜めの辺を前にしていた。実物は垂直の柱が前、斜めの支柱が後ろ） | ① 写真を見ずに知識だけで形を描いた（③ の部品）。② 前から見た U 字（耳）の印象だけで、横から見た抜けを確かめなかった。③ 調査で長さなどの**数値**だけを調べ、形の成り立ち（穴・分かれ目・向き）を調べなかった。数値は穴の有無を教えてくれない。④ 向きの決め手を確かめなかった | 1. 作る前に、参照品の**単体の側面写真**を 1 枚以上用意する（無ければ作者に依頼）。知識だけで描いた部品は「③ 未照合」に入れ、照合するまで確定扱いしない。 2. 写真で次を確認してから作る: **抜け**（窓・穴・部品の間のすき間）／**分かれ目**（一体か、別部品か、輪が 1 つか 2 つか）／**向き**（どちらが銃口側か）／**可動部の向き**（スイベルの回転軸など）。 3. 向きは**機能で決める**（着剣ラグは銃口側へ突き出す、ガスチューブは後ろから入る等）。見た目の印象で決めない。 4. 写真の縮尺は**互いに独立した既知寸法 2 つ以上**から決め、残りの寸法で食い違いがないか確かめる（今回は長さの公称値 1.625in で縮尺を取ると、輪の下面が銃身の中に入ってしまい矛盾した）。 5. 作ったら `inspect_views.py --photo` で輪郭を写真に重ねて確認する |
| グリップ（A2） | Engage 型（別製品）の写真を写して作った | 参考写真の製品名・型番を確かめずに写した | 写真を使う前に、写っている部品のメーカー・型番が作りたい参照品と同じかを確かめる |

### 作り方の考え方: 部品ごとに作る＋配置の基準を 1 か所に 🟡 仮

「部品ごとに作れば崩れた銃になりにくい」は半分正しい。グリップやトリガーのように**部品単体の形**は部品ごとに作ると安定した。
しかし試作で「崩れて見えた」原因の多くは**部品同士の位置関係**だった（上部レシーバーが 30〜40mm 前にずれていた、弾倉の差し込みが浅い、
バッファチューブとストックの位置、グリップ上面とレシーバー下面の不一致、フロントサイトの位置）。部品を正しく作っても取付位置が狂えば崩れる。

1. **部品は個別に作る**（`ar15_parts.py` の関数 1 つ＝部品 1 つ。単体の `.geo.json` にも出す）。
2. **配置の基準は 1 か所に集め、実寸で決める**（`ar15_parts.Layout`: ボア軸の高さ、レシーバー前後端、ボルトフェイス、ガスポート、
   マグウェル、ストック位置など）。部品は基準からの寸法で置き、他の部品の位置を直接書かない。
3. **順番**: 全体を 1 枚描いて基準（全長・各部の位置）を確認してから、部品の細部に入る。
4. **取付面は相手側から**: 部品同士が接する面は、相手部品（レシーバー等）の実測から取る。グリップを替えてもレシーバー側の面は変わらない。
5. **参照品を先に調べる**: 部品を作る・直す前に、参照する実物のメーカー・型番・取付方法・寸法を調べて「部品ごとの参照品」の表に書く。
   形を見て直すのはその後（例: FSB は調べた結果、モデルが実物の約 6 割の長さだった）。
   数値だけでなく**形の成り立ち（抜け・分かれ目・向き）も単体の写真で確かめる**（→ 上の「形の読み違いの記録と対策」）。

- **比較の観点**: 1丁あたりの作成時間／作者の修正量／キューブ数・テクスチャ解像度（描画負荷）／一人称・三人称での見え方／アタッチメント装着時の破綻の有無。
