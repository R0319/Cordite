# 06. アニメーション仕様 🟡 仮

> **範囲**: 一人称（主観）／三人称（客観）アニメーションの一覧。
> 用語・凡例は [README.md](README.md) を参照。
>
> ⚠️ **アニメーション本体（モーションデータ）は作者が手作業で制作する。Claudeは生成・レビュー対象外。**
> Claudeが担当するのは「アニメーションを再生する側のコード（トリガー条件・状態遷移・同期）」まで。
> モデルのボーン構成と連動 → [07-model-assets.md](07-model-assets.md#ボーン命名規約重要アニメーションと連動)。

## アニメーション作成方式 🟡 仮

- **GeckoLibなど外部アニメーションライブラリは使用しない。軽量な自作アニメーションエンジンを実装する。**
  - 理由: パフォーマンス最優先（PvPでの多人数プレイヤーおよび `04-enemies.md` / `09-npc.md` の武装NPC大量発生を想定すると、汎用ライブラリの抽象化オーバーヘッドを避けたい）。
  - 一人称視点武器特有の処理（視点変換・リコイル・エフェクト同期）はどのみち自作が必要なため、外部ライブラリで肩代わりできる範囲（ボーン読み込み・キーフレーム補間）は限定的。
- **モデル/アニメーションのファイル形式**: Blockbench標準搭載の「Bedrock Edition」エクスポート形式（`geometry.json` + `animation.json`）を採用。GeckoLib専用のBlockbenchプラグインは不要（Blockbench標準機能のみで作者が制作可能）。
- ランタイム側は上記JSONを自前でパースし、[07-model-assets.md](07-model-assets.md#ボーン命名規約重要アニメーションと連動) のボーン名に対応する変換行列を毎フレーム計算する軽量パーサ／補間器を実装する。
- **自前パースの技術的前提（🟡仮・`docs/design/animation-system.md` で最終確定）**:
  - **座標系・回転の変換が必要**: Bedrock geometry/animation は Java版レンダリングと軸の向き（Xミラー）・回転の符号規約が異なる（GeckoLib等の既存実装は内部で補正している）。パーサ/レンダラ側で変換を実装し、実装初期に単純なテストアニメ1本で軸・符号を検証する。
  - **`format_version` を固定**: Blockbenchのエクスポートスキーマは複数バージョンがある。対応するバージョンをピン留めし、それ以外はロード時に警告を出す。
  - **Molang 非対応**: キーフレーム値は数値リテラルのみをサポートする（Molang式は解釈しない）。制作側の制約 → [07-model-assets.md](07-model-assets.md#制作上の制約重要)
  - **サウンド/パーティクル名のマッピング**: `sound_effects` / `particle_effects` に書く名前はBedrockのイベント名ではなく、Cordite側で解決できるID（Java側の SoundEvent / パーティクルへの対応表）とする。
- 詳細設計（パース方式・補間アルゴリズム・状態遷移の持ち方）は実装直前に `docs/design/animation-system.md` を書く。

## モデル構成（一人称/三人称分離）🟡 仮

- **viewmodel（一人称用）と worldmodel（三人称用）は別モデルとして用意する**（1モデル共用にはしない）。
  - 理由: 一人称は手元での見え方（誇張パース・壁めり込み防止）を優先した専用モデルが必要なため。
  - ボーン命名規約（[07-model-assets.md](07-model-assets.md#ボーン命名規約重要アニメーションと連動)）は両モデルで共通にし、アニメーション再生コードを両者で共有する。
  - アニメーションデータ（`animation.json`）自体もviewmodel用／worldmodel用で別々に用意する想定（同じ動作でもボーン配置・スケールが異なるため）。

## 発射エフェクトのタイミング方式 🟡 仮

- **発射音・薬莢排出・マズルフラッシュ等のタイミングはアニメーションファイルに埋め込む方式を採用**（gunpack側で別途タイミング数値を持たない）。
  - Bedrock Edition の `animation.json` は `sound_effects` / `particle_effects` / タイムラインキーフレーム等の欄を標準で持つため、この標準フィールドをそのまま読む。
  - 理由: 軽量性を優先する場合、既に解析対象になっている1ファイルの標準フィールドを使う方が、gunpack JSON側に別のタイミング管理システムを二重に持つより実装・実行コストが低いため。

## 一人称の手・腕表示（ハンドアンカー方式）🟡 仮

- viewmodel（一人称銃モデル）に **`right_hand` / `left_hand`** という基準ボーンを持たせ、銃のアニメーション（リロード・ADS等）に合わせてこのボーンも動かす。コード側は毎フレームこのボーンのtransformを読み取り、腕モデルをそこに追従させて描画する（TACZ等の既存ガンMODで実績のあるハンドアンカー方式を参考に採用）。
  - 理由: 銃単体のアニメーションだけでは手・腕が映らず不自然になるため。腕を別途手付けアニメーションしなくても、銃側のボーンに追従させるだけで自然に見える。
  - ボーン定義 → [07-model-assets.md](07-model-assets.md#ボーン命名規約重要アニメーションと連動)
  - プレイヤーモデルとの比率差を補正するスケール値（TACZはY軸1.5倍等）が必要になる可能性がある。具体的な数値・実装方式は実装直前の `docs/design/animation-system.md` で詰める。
  - worldmodel（三人称）には適用しない。三人称の腕・体は下記「プレイヤー本体（腕・体）のポーズ」で別途扱う。

## プレイヤー本体（腕・体）のポーズ 🔵 検討中

- 上記のハンドアンカー方式は**一人称のみ**。三人称で見えるプレイヤーの腕・体の構え（照準時の姿勢、伏せ等）をどう制御するかは別途**未決定**。自作するか、軽量な既存ライブラリ（TACZが採用しているような player animator 系）を使うか、どちらでも可という方針。
- 判断基準は他の項目と同じく軽量性 → [パフォーマンス方針](#パフォーマンス方針-仮)。実装時に候補を比較して決定する。

## パフォーマンス方針 🟡 仮

**なるべく軽量に動作させることを最優先とする。** 実装直前の詳細設計（`docs/design/animation-system.md`）はこの方針を踏まえて具体化する。

- **キーフレームデータは事前ベイク**: `geometry.json`/`animation.json` はロード時に1回だけパースし配列化してメモリ保持。毎フレームJSON処理はしない。
- **不動ボーンの計算スキップ**: `receiver`/`barrel`/`handguard`等の固定ボーンは相対行列を1回計算してキャッシュし、可動ボーン（`bolt`/`magazine`/`trigger`等）のみ毎フレーム再計算する。
- **非表示インスタンスは評価しない**: フラスタム外・画面に映っていないプレイヤー/NPCの武器はボーン計算自体をスキップする。
- **同時アニメーションレイヤー数を絞る**: TACZのような「idle+recoil+sway+reload常時同時合成」ではなく、まずは1インスタンスにつき同時1〜2アニメーションのシンプルな状態機械から始め、必要な分だけレイヤーを増やす。
- **三人称表示はLOD的に簡略化してよい**: 自分の一人称視点武器は精密でよいが、画面内に大量出現しうる他プレイヤー・NPCの三人称武器アニメーションは更新頻度を落とす／ボーン数を減らすなど軽量版描画の余地を残す。
- **補間は必要最小限**: 回転補間は基本オイラー角の線形補間で足り、精度が要る箇所（大きな回転を伴う一人称視点変換等）だけ球面線形補間（slerp）等の重い計算を使う。
- **描画詳細度（LOD）はクライアント設定で段階的に変更可能にする**: 上記の三人称簡略化はデフォルトで自動適用するだけでなく、プレイヤーが明示的に品質を選べる設定項目にする（重いPC/軽いPCの両方に対応するため）。
  - 例（🟡仮・段階数や名称は要検討）: 高＝全ボーン毎フレーム更新・フルレイヤーブレンド／中＝三人称の更新頻度を間引く（例: 数フレームに1回）・同時レイヤー数を制限／低＝三人称ボーン数を削減した簡略モーションのみ
  - **一人称視点（自分の武器）の見た目品質には影響させない**。LODは他プレイヤー・NPCの三人称描画のみが対象。
  - あくまで見た目（クライアント側描画）のみに影響し、命中判定・弾道・クールダウン等のサーバー権威ロジックには一切影響させない（[../design/00-architecture.md](../design/00-architecture.md#設計原則) のサーバー権威原則を維持）。
  - 実装は既存の `config` パッケージのクライアント設定に追加する想定。詳細は `docs/design/animation-system.md` で設計。
