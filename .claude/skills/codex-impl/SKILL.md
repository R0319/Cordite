# Codex への実装委譲

このプロジェクトの役割分担: **Claude** = 設計書・調査・エラー解析・レビュー・ビルド、
**Codex** = 設計書に沿ったコードの実装、**作者** = アセット制作・見た目調整・実機確認。

Codex 向けの恒久ルールは `AGENTS.md`（Codex が自動で読む）。**同じことを `codex-task.md` に
書き直さない**（トークンの無駄）。指示書には**今回の作業だけ**を書く。

## 手順

### 1. 実装判断を先に決着させる

Codex は「設計書に書かれていない仕様を勝手に決めない」規約なので、判断が必要な点を残すと止まって帰ってくる。
新機能なら `docs/design/<feature>.md` を先に書く。小さなバグ修正なら指示書に直接書けばよい。

**原因の特定は Claude 側でやる。** 「これがおかしいので調べて直して」ではなく
「ここがこうなっているのが原因なので、こう直せ」まで落としてから渡す方が速く、ブレない。

### 2. `codex-task.md` を書く

リポジトリ直下の `codex-task.md`（`.gitignore` 済みの使い捨て）。書く内容:

- **作業範囲を明示的に区切る** — 「Step 1〜6 のみ」「このファイルには触るな」
- **現象 → 原因 → 修正方針** の順（原因が特定済みならそう明記する。Codex に再調査させない）
- 参照すべき既存ファイル・踏襲すべき書式（このリポジトリは**Javadocが厚め**で「なぜそうしたか」を
  日本語で書く文化がある、と必要に応じて念押し）
- 変更してほしくない既存挙動を明記（例:「補完・権限レベル2・エラーメッセージの既存挙動は変えるな」）
- 末尾に必ず:
  ```
  ## 共通の注意
  - ビルドは実行しなくてよい（Claude側で回す）
  - 見た目の配置定数は作者が実機で調整する領域なので変更しないこと

  ## 最終メッセージに書くこと（日本語で、簡潔に）
  - 変更ファイル一覧と修正内容
  - 確信の持てなかった箇所
  ```

複数件をまとめて渡してよい（過去実績あり）。その場合は `## 1.` `## 2.` と番号で区切る。

### 3. Codex を呼ぶ

`mcp__codex__codex` ツールを次のパラメータで:

| パラメータ | 値 |
|-----------|---|
| `prompt` | `codex-task.md を読み、その指示に従って実装してください。` |
| `cwd` | リポジトリのルート（絶対パス。実際の値は git管理外の `CLAUDE.local.md` を参照） |
| `sandbox` | `danger-full-access` |
| `approval-policy` | `never` |

**`sandbox` は `danger-full-access` 以外を使わない。** この Windows 環境では Codex のサンドボックスが
一切起動できないことが検証済み（`CreateProcessAsUserW failed` / `Windows error 5`）。`elevated` /
`unelevated` の両方、`codex exec` 直叩き・MCP 経由のどちらでも失敗する。

プロンプトは短く保つ（指示書を読ませる形にすることでトークンを節約する設計）。

### 4. 実行中の様子を見る（必要なら）

MCP の戻り値は **Codex の最終メッセージだけ**。途中のコマンド・思考は含まれず、
120秒を超える呼び出しはバックグラウンドタスクへ退避される。途中経過を見たいときはセッションログ:

```powershell
.\codex-watch.ps1            # 直近セッションの最後30件
.\codex-watch.ps1 -Follow    # 実行中をリアルタイム追跡
```

作者から「codex が今何をしているか見たい」と言われたらこれを案内する。

### 5. 差分を確認する（省略しない）

サンドボックス無しで動いている以上、**ここが唯一の実効的な歯止め**。

```
git diff
git status          # 意図しない新規ファイルが無いか
```

見るポイント:
- **アセット**（`.geo.json` / `.png` / `.animation.json` / `.ogg`）に触れていないか
- **見た目の配置定数**（一人称の位置/回転/スケール、ロケーター座標、アイコンサイズ）を変えていないか
- **サーバー権威**を崩していないか（クライアントから発射数・ダメージ・方向を申告させていないか）
- コメント・Javadoc が日本語で、周囲のスタイルに合っているか
- 勝手にコミットしていないか（`git log` で確認）

**大きな変更の前に作業ツリーをコミットしておく**（未コミットの作業は git の保護外）。

### 6. ビルドして、ダメなら 2 へ戻る

`build-check` スキルの手順で `./gradlew build`。エラーが出たら原因を解析し、
**修正指示を `codex-task.md` に書き直して** ステップ3へ戻る。

武器・ダメージ・同期・パケットに触る変更だった場合は、ビルドが通ったあと `mc-reviewer` を通す。
設計書と実装がズレたら `mc-doc-sync` で追従漏れを洗う。

### 7. 作者へ返す

ビルドが通ったら、実機で確認すべき点をチェックリストで渡す（`asset-apply` の ③ 参照）。
Codex が「確信が持てなかった」と書いてきた箇所は**必ずそのまま作者に伝える**（握り潰さない）。
